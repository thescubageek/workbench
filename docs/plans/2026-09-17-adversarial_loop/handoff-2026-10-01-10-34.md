### Discoveries Not in Documentation

- **The design is stale against the code.** `docs/plans/2026-09-28-guard_lexer_and_pr_identity/design.md` (Resolved Decisions, Q3 and A1) defines "own checkout" as `headRefOid` descent only. Round 11 added the branch-name test in three blocks, and the design was never updated. The design also says a cross-repository PR is "refused by name", while the code fetches it. Treat that design as superseded input, not as the contract.
- **The identity is communicated by a printed line.** `adversarial-review` prints `identity: <review_provenance>`, and `adversarial-loop` Phase 0 decides by whether that line starts with `HEAD`. Each Bash call is a fresh shell, so the model carries the values between blocks. A prefix test on free text is the shared weakness: `HEAD-fix` matches, and `feature-B (branch; …)` does not.
- **Measured identity lines** (round-12 `/verify`, scratch repo, stub `gh`): PR 42 stacked gives `origin/pr/42 = …, fetched`; no target gives `HEAD (current branch; base origin/main)`; branch target `feature-B` (the current branch) gives `feature-B (branch; …)`; branch target `feature-A` gives `feature-A (branch; …)`. Round 13 added: branch target `HEAD-fix` gives `HEAD-fix (branch; …)`.
- **Step 8 stages a plan before the stop rule applies.** `adversarial-review/SKILL.md:514` ("Having written it, stage it") writes and `git add -f`s `reviews/<date>-round-N/tasks.md` under the `--plan` directory, whatever the identity is.
- **Phase 2's push goes to the branch's upstream remote.** No identity check compares that remote with the PR's repository. A two-remote clone (origin = fork, upstream = parent, same-repo PR in the parent) could push to the fork and un-draft the parent PR. This was ledgered Pre-existing and `gh`'s remote ranking was not verified.
- **`gh` placeholder and remote behaviour is unverified here.** Verify `gh repo set-default --view` and `gh pr view --json url` in a real two-remote clone before designing around it.

### Edge Cases Discovered

1. **A branch target that names the current branch** prints a non-`HEAD` line, so the loop stops after step 2 for the branch you are on. Confirmed in `/verify`.
2. **A branch named `HEAD-fix`** passes the `HEAD` prefix test. `git check-ref-format --branch` accepts it.
3. **A zero-finding first round** creates no ledger file, so the pre-round-12 ledger block exited 128. Round 12's guard fixed that and now hides a mistyped ledger. A clean round writing an explicit row is the candidate fix.
4. **Detached HEAD**: Phase 2 refuses, and reply-to-claude's remedy text still says "push this branch", which cannot apply.

### Open design questions

- What are the values of "the target relative to this checkout"? Candidates from the history: own PR checkout, stacked on the PR head, renamed local branch, detached HEAD, same-name fork, cross-repository, branch target equal to the current branch, branch target merely prefixed `HEAD`, no argument, path target, two remotes.
- Should the resolver emit a structured field (`own_checkout=true|false` plus a reason) that the loop reads, so no consumer parses free text?
- Should the loop run only on its own checkout, with a standalone review as the only entry for any other target? That would remove the stop rule, the fetch-side fixes and the staged-plan problem together.
- When the target is not the checkout, may the review write or stage a plan at all? What owns the dispositions?
- What must a publishing block check beyond the PR's own facts: the push destination, the remote, the branch's upstream?
- How are the fenced blocks tested, given each round has found its defects by executing them?
